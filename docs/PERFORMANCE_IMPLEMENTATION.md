# KëshillaKos performance implementation

Implemented the five requested fixes without redesigning the pages or changing business rules. No deployment or database index changes were made. Temporary baseline and optimized servers used the same configured database, with automatic index/collection creation disabled.

## Changes

1. Replaced the external 2000×2998 homepage hero with centered landscape crops (960×540, 1440×810, 1920×1080) and mobile crops (480×800, 768×1280), in AVIF and WebP. The existing photo, centered cover behavior and gradient overlays remain. Images load eagerly with high fetch priority. Encoding used sharp: AVIF quality 48 and WebP quality 72.
2. Lazy-loaded non-home routes, including dashboards, admin panels, editors, messaging and calendars. Firebase loads with authentication routes/use, rather than the homepage. GoogleAuthButton loads the popup SDK before the user clicks.
3. Marketplace requests only active rows. Inactive tabs use count-only responses. Search waits 300 ms; both request effects retain AbortController cancellation and ignore aborted responses. Inactive counts do not refresh on page/limit/sort changes.
4. Marketplace serializers reuse aggregation ratings. Other callers use four batched collection reads rather than per-account rating lookups. Manager/owner eligibility, weighted account-wide ratings and verified counts remain intact. Empty offer lists skip enrichment reads. Legacy service serialization retains its existing rating behavior.
5. Added compression 1.8.2 (Brotli/gzip negotiation). Public configuration uses `public, max-age=300, must-revalidate`. Public marketplace lists use `public, max-age=0, must-revalidate`, retaining immediate revalidation after mutations. Private routes are excluded; errors use `no-store`. Existing immutable media caching remains.

Bytes use decimal KB. Backend times are medians of five warmed, sequential requests per endpoint, measured locally against the same remote database. These are not production mobile LCP/INP benchmarks. Baseline source was extracted from HEAD into a temporary directory; optimized measurements used the production build.

The main JS entry is about 517 KB, but the table correctly counts **all 18 initial JS chunks** (877 KB), not just the entry. Remaining routes/Firebase are deferred. Total code is split, not deleted. The entry still triggers Vite’s existing 500 KB chunk-size warning.

Inactive provider counts return 113 bytes; inactive service counts return 108 bytes. Their final timing samples are recorded below:

- `/api/providers?countsOnly=true`: 55 ms median, 113 bytes.
- `/api/services?countsOnly=true`: 61 ms median, 108 bytes.

Initial services-tab traffic is now 10,763 + 113 decoded bytes, rather than 10,763 + 2,446. Pagination requests only active rows. The 300 ms debounce is implemented and statically checked; browser interactions confirmed search/tab behavior, but the browser session did not expose a reliable request trace, so request-count reductions are based on the code paths rather than a measured browser waterfall.

Configuration endpoint execution time is largely unchanged; the benefit is compression and browser cache reuse for five minutes, rather than a claimed server query improvement. Samples vary with remote database/network latency.
